# 用户池化邮箱管理重构计划

## 一、需求理解

本次需求的目标，是把当前“单管理员 + 全局邮箱池”的 Outlook Mail Station，升级为“管理员管理多个用户，每个用户拥有独立邮箱池，用户按现有租约逻辑随机消费/释放邮箱，左侧列表仅展示已消费邮箱”的新模型。

核心业务变化：

1. 新增用户管理能力，管理员可管理用户，并查看每个用户的邮箱池分配情况。
2. 每个用户默认拥有独立账号池；邮箱导入后进入该用户池，而不是直接出现在左侧常用面板。
3. 用户点击“随机邮箱”后，从自己的池中消费一个邮箱，并沿用当前 lease / release 锁定逻辑。
4. 管理员可查看所有用户、池内邮箱、已消费邮箱，但不能代替用户消费邮箱。
5. 左侧列表改为“当前用户已消费邮箱列表”，只有消费后才出现。
6. 按钮面板新增“随机邮箱”按钮，点击后消费并加入左侧列表；列表项新增“释放”按钮，点击后放回池中。

## 三、构思方案

### 方案一：单表扩展方案

方案名称：单表扩展方案：在 `OutlookAccount` 上新增 owner / consumer / status 字段，用一张表同时表示“用户池邮箱”和“已消费邮箱” | 优点：改动较小、迁移简单、复用现有接口更直接 | 缺点：语义耦合严重，后续审计、消费历史、池视图与消费视图会越来越难维护。

### 方案二：用户 + 池 + 消费视图分离方案

方案名称：用户池化分层方案：新增用户实体，`OutlookAccount` 负责邮箱资产归属，消费关系单独建模或至少单独抽象为“当前消费视图”，让池内邮箱与已消费邮箱在接口层明确分离 | 优点：业务语义清晰，便于实现“admin 可看不可消费”“左侧只展示已消费邮箱”“池与消费分视图管理”，后续可扩展审计与权限 | 缺点：接口、状态与前端页面改造更大。

### 推荐方案

推荐 **方案二：用户池化分层方案**。

原因：本次需求已经从“单管理员管理邮箱”升级为“多用户 + 用户池 + 消费列表 + 管理员只读监管”，如果继续在原有单表语义上叠加字段，短期可做，长期会明显恶化维护性。

## 四、实施计划

### 步骤 1：重构数据模型与初始化迁移

涉及文件：

- `backend/app/models.py`
- `backend/app/database.py`
- `backend/app/schemas.py`

计划内容：

1. 新增后台用户实体（如 `StationUser`）：
   - 字段建议：`id`、`username`、`password`、`role`、`enabled`、`created_at`、`updated_at`
   - 角色至少区分：`admin`、`user`
2. 扩展 `OutlookAccount`：
   - 增加 `owner_user_id`，表示邮箱归属到哪个用户池
   - 保留现有 `lease_expires_at` / `last_leased_at`，继续作为消费锁定机制
3. 增加“当前消费关系”表达：
   - 推荐新增单独消费表（如 `ConsumedMailbox` / `UserMailboxLease`）
   - 记录：`user_id`、`account_id`、`leased_at`、`lease_expires_at`、`released_at`
   - 若实现上为简化可只保留“当前有效消费关系”，但接口层仍要分离池内/已消费语义
4. 在 `database.py` 中补充旧库迁移逻辑：
   - 新表创建
   - `outlook_accounts` 增量字段补齐
   - 预置 admin 用户初始化策略

### 步骤 2：重构鉴权与角色身份识别

涉及文件：

- `backend/app/auth.py`
- `backend/app/routers/admin_auth.py`
- `backend/app/main.py`
- `backend/app/schemas.py`

计划内容：

1. 将当前单一管理员登录扩展为“后台用户登录”。
2. 登录响应中返回用户角色、用户标识等最小身份信息。
3. 鉴权层支持区分：
   - admin：可查看所有用户、所有邮箱池、所有已消费关系，但不能消费他人邮箱
   - user：只能查看自己的池和自己的已消费邮箱
4. 保持已有开放 API 与公开分享页面逻辑不受本次后台角色重构影响。

### 步骤 3：重构导入、池视图、随机消费与释放接口

涉及文件：

- `backend/app/routers/accounts.py`
- `backend/app/routers/open_api.py`
- 可能新增 `backend/app/routers/users.py`
- 可能新增 `backend/app/routers/pools.py`

计划内容：

1. 新增用户管理接口：
   - 用户列表
   - 用户创建/编辑/启停
   - 查看用户池统计
2. 调整导入逻辑：
   - admin 导入时必须明确导入到哪个用户池
   - 导入结果不再默认进入左侧已消费列表
3. 新增“池视图”接口：
   - 查看某用户池中的邮箱
   - 查看某用户已消费邮箱列表
4. 新增/改造“随机邮箱消费”接口：
   - 普通用户从自己的池中随机领取一个未被占用邮箱
   - 创建消费关系并写入租约时间
   - 同时保证与现有 release 逻辑兼容
5. 新增/改造“释放邮箱”接口：
   - 仅允许释放当前用户自己消费的邮箱
   - 释放后从左侧已消费列表移除，并放回用户池
6. admin 相关接口只提供查看能力，不提供代消费入口。

### 步骤 4：重构前端信息架构与页面交互

涉及文件：

- `frontend/src/pages/MailStationPage.tsx`
- `frontend/src/components/AccountSidebar.tsx`
- `frontend/src/types.ts`
- `frontend/src/lib/api.ts`
- 可能新增用户管理相关页面/组件

计划内容：

1. 左侧列表语义改为“当前登录用户已消费邮箱”。
2. 导入完成后，左侧列表不自动出现邮箱。
3. 在按钮面板新增“随机邮箱”按钮：
   - 点击后调用随机消费接口
   - 消费成功后加入左侧列表并自动选中
4. 左侧列表项新增“释放”按钮：
   - 点击后调用释放接口
   - 成功后从列表中移除
5. admin 视角增加用户管理与池查看入口：
   - 查看用户列表
   - 查看用户池邮箱数量、已消费数量
   - 查看具体邮箱，但不提供消费按钮
6. 当前详情区需兼容“未消费时无当前邮箱”的空状态。

### 步骤 5：调整主页面状态流与兼容策略

涉及文件：

- `frontend/src/pages/MailStationPage.tsx`
- `frontend/src/App.tsx`
- 相关样式文件

计划内容：

1. 首屏加载逻辑改为：
   - user：先加载“我的已消费邮箱列表”，若为空则展示空状态和“随机邮箱”引导
   - admin：默认进入用户管理/总览视图，或保留当前主站布局但切换为只读模式
2. 邮箱详情加载、邮件同步、发件、分享能力只对“当前已消费邮箱”生效。
3. 若 admin 查看某用户邮箱详情，应限制会触发消费语义的入口。

### 步骤 6：自检与验收

计划验收维度：

1. admin 能创建/查看用户，并查看用户池与已消费情况。
2. 导入邮箱能明确归属到某个用户池。
3. 普通用户点击“随机邮箱”能从自己的池消费一个邮箱。
4. 消费后邮箱出现在左侧列表，释放后从左侧移除并回到池中。
5. admin 能看见邮箱信息，但不能消费别人的邮箱。
6. 现有发件、同步、临时授权能力在“已消费邮箱”语义下可继续工作。

---

## 五、实施时的关键注意点

1. 这是高风险重构，涉及：
   - 数据模型变化
   - 鉴权角色变化
   - 现有前后端主流程变化
2. 需优先保证旧数据可迁移，避免已有邮箱因字段新增而不可用。
3. 随机消费与 release 的约束要明确“当前操作者是谁”，否则会出现越权释放。
4. 建议优先完成后端模型与接口，再联调前端视图。
